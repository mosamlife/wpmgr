# apps/api/db/rls-cross-tenant-policies.txt
#
# Every RLS policy in this database that grants access ACROSS tenants, with the
# access mode it is meant to have recorded as a DECISION rather than left to a
# default nobody typed.
#
# Checked by scripts/check-rls-cross-tenant.sh against a live pg_policies.
# Regression suite: scripts/check-rls-cross-tenant_test.sh.
#
# ---------------------------------------------------------------------------
# WHY THIS FILE EXISTS (GH #470)
# ---------------------------------------------------------------------------
#
# `CREATE POLICY` defaults to `FOR ALL`. A policy that is correctly FOR ALL and
# one that is wrongly FOR SELECT are visually identical, because the clause the
# bug turns on is the one nobody writes. Under FORCE ROW LEVEL SECURITY a
# FOR SELECT policy admits the read and admits nothing to the write, so an
# UPDATE or DELETE on that path matches ZERO ROWS WITH NO ERROR. PostgreSQL
# applies the UPDATE policy to SELECT ... FOR UPDATE as well, so even the
# locking read comes back empty.
#
# Not a failure -- a silence. It has shipped three times:
#   m84/#96    backup_schedules   every backup schedule stopped advancing
#   m89/#131   update_tasks       the stale-task reaper swept nothing
#   m118/#463  update_runs        the deferred dispatcher claimed nothing
#
# Two of those post-mortems are written into db/schema.sql, next to the
# policies they are about.
#
# The other half of #470 is that the construct is NOT CONSISTENTLY NAMED, so an
# audit that greps a naming convention returns FALSE NEGATIVES -- the direction
# that costs a tenant boundary. Run the guard and read the NAMING section: it
# counts the variants against the live database rather than quoting a number
# here that would rot. One of the outliers is backup_schedules_scheduler, which
# IS the m84/#96 fix, so a name-based sweep misses the very policy the first
# post-mortem is about.
#
# The guard therefore never greps a name. It enumerates from pg_policies and
# classifies on the GUC each policy's expression tests.
#
# ---------------------------------------------------------------------------
# WHAT COUNTS AS CROSS-TENANT
# ---------------------------------------------------------------------------
#
# A PERMISSIVE policy whose predicate does not BIND the row's tenant_id column
# to app.tenant_id. That is a property of the expression, not of the name.
#
# BOUND, NOT MENTIONED. Reading the setting is not the same as constraining the
# row with it: USING (current_setting('app.tenant_id', true) <> '') reads it and
# hands over every row in the table. Such a policy is a cross-tenant grant and
# is audited as one; the guard's UNBOUND TENANT SETTING section calls it out
# rather than letting a ledger row be added to silence it.
#
# THE PREDICATE IS `USING`, OR `WITH CHECK` WHEN THERE IS NO `USING`. A FOR
# INSERT policy has no USING at all -- there is no existing row to test -- so
# its whole condition lives in WITH CHECK. Reading only USING classified every
# INSERT policy as a cross-tenant grant, including the three RUM ingest
# policies whose WITH CHECK pins tenant_id to app.tenant_id. Those three were
# in this file and are not any more: they are tenant-bound, and a ledger row
# asserting a grant that does not exist costs the file the only thing it has,
# which is being true.
#
# RESTRICTIVE policies are excluded deliberately: a restrictive policy can only
# narrow the row set, never grant one. The site_scope policies are restrictive
# and do not mention app.tenant_id, so a classifier that ignored `permissive`
# would flag all of them as cross-tenant grants and bury the real signal.
#
# A CONSEQUENCE WORTH STATING: this file therefore does NOT answer "is this
# table site-scoped". Neither does the guard. See the header of
# apps/api/db/schema.sql for what does.
#
# ---------------------------------------------------------------------------
# FORMAT
# ---------------------------------------------------------------------------
#
#   table|policy|guc|cmd|ops|rationale
#
# guc   The settings the policy's USING/WITH CHECK expressions read, sorted and
#       comma-joined. '-' when the expression reads none (USING (true)).
#       This is the field the audit is built on.
#
# cmd   The access mode the policy is MEANT to have: ALL, SELECT, INSERT,
#       UPDATE or DELETE. The guard fails if the database disagrees, in either
#       direction -- a policy that drifted, or a ledger edited without the
#       migration.
#
# ops   The operations the code path behind this policy actually performs,
#       comma-joined, from: select insert update delete lock
#
#       RECORD THIS HONESTLY AND PER POLICY. Write down what the path does, not
#       what this policy happens to admit. Do NOT trim an operation because a
#       sibling policy covers it -- the guard understands siblings, and a
#       trimmed entry is a lie that survives until the sibling is dropped.
#
#       `lock` means SELECT ... FOR UPDATE/SHARE. It is covered only by ALL or
#       UPDATE, because PostgreSQL applies the UPDATE policy to a locking read.
#       Note also that UPDATE ... RETURNING needs `select` as well as `update`:
#       SELECT policies apply to the returned rows.
#
#       COVERAGE IS CHECKED PER TABLE, NOT PER POLICY, because PostgreSQL ORs
#       permissive policies per table per command. The guard takes the union of
#       `ops` across a table's cross-tenant policies and requires every one to
#       be covered by at least one of the modes those policies carry.
#
#       That is what makes a SPLIT PAIR legal: autologin_tokens carries a FOR
#       SELECT policy for the read and a FOR UPDATE policy for the consuming
#       write, and together they cover the path. A per-policy check would
#       redden that correct pair, and the "fix" it implies is a migration
#       widening a cross-tenant grant to silence a false positive. Splitting is
#       also the tighter remedy for a real #96 finding -- it grants exactly one
#       extra verb -- so the guard has to understand the shape it recommends.
#
#       '-' means the path was not audited operation by operation. It is ONLY
#       legal on a FOR ALL policy, where every verb is admitted and the
#       silence cannot arise. The guard rejects '-' on any narrower mode: a
#       policy narrower than ALL has to carry the evidence that the narrowing
#       is safe.
#
# ---------------------------------------------------------------------------
# THE DECISION ON STATING `FOR ALL` EXPLICITLY (#470 item 3)
# ---------------------------------------------------------------------------
#
# The issue asks whether `FOR ALL` should be written out everywhere so a
# reviewer sees the clause instead of inferring the default. Recorded answer:
#
#   * NEW migrations state the mode explicitly, always. m118 already does, and
#     that is the standard from here.
#
#   * Existing policies are NOT rewritten just to add the word. An applied
#     migration is immutable, so "everywhere" would mean a new migration that
#     DROPs and reCREATEs most of the cross-tenant policies in this file for a
#     purely cosmetic change -- a large, irreversible, self-inflicted diff over
#     the tenant boundary, taking real locks at boot inside main(), to make a
#     default visible.
#
#   * This file is what makes the mode visible instead, and unlike a clause in
#     a migration it is CHECKED against the live database on every run. A
#     migration's text is history; this is the current state, reconciled.
#
# Reviewed by security-reviewer as part of #470.
#
# ---------------------------------------------------------------------------

# ---------------------------------------------------------------------------

# the line it prints. Answer the question first: does anything running under
# that GUC write to that table, or take a row lock on it? Then record the
# answer. The value of this file is that somebody had to look.
#
